# ROVOR AI: source-grounded executable evaluation pack

**Implemented scope:** a deterministic offline acceptance/evidence test, not a model benchmark, deployed ghost employee, approved client deliverable or finished animated video.

## Included artifacts

- `cases.json`: three source-bounded cases—fictional client intake/delivery, fictional observed-vs-inferred sales research, and the actually reported PR #24 pre-job Actions failure.
- `good-answers.json`: source-preserving example outputs, NOT generated by a model.
- `bad-answers.json`: deliberately false answers that must be rejected (invented price/revenue loss, unauthorized sending, unearned approval and unverified CI root cause).
- `evaluate.py`: stdlib-only deterministic checker; no network, model, credentials or side effects.
- `test_evaluate.py`: 21 tests including CLI behavior, case validation and explicit false-claim regressions.

## Source grounding

Workflow expectations derive from merged repository files: `business/templates/client-intake.md`, `business/templates/opportunity-brief.md`, `business/templates/delivery-review.md`, `business/proof-catalog.md`, `business/offers/first-offer-draft.md`, `ROVOR-AI-PLAN.md`, and `architecture/CHATGPT-WORKFLOWS.md`. The CI fixture uses observed [PR #24 Actions run #39683961823](https://github.com/TeamRovor/rovor-video-engine/actions/runs/39683961823) as documented in `coordination/hosted-runner-diagnosis.md`.

**Important:** Customer and site examples are labeled fictional; CI metadata is a dated snapshot, not real-time status. A missing GitHub Actions `steps` array does not prove that Python tests ran, that the Actions incident caused the failure, or that paid minutes are exhausted.

## Reproduce from this directory (Python 3.9+, no installs)

```sh
python -m unittest -v test_evaluate
python evaluate.py --answers good-answers.json
python evaluate.py --answers bad-answers.json --expect fail
python evaluate.py --answers good-answers.json --report evaluation-report.json
```

Reports are JSON with pass/fail counts and issue codes. Exit status is zero only if all provided results match the `--expect` condition. `--expect fail` means the intentionally incorrect outputs were rejected; it is not a business-delivery success.

## How to apply to ROVOR AI

Gather actual approved source references, exact known fields, unresolved fields, permitted claims and actions in a new case. Have a human independently approve the ground truth. Generate a structured candidate response; evaluate it; save the resulting report with source version/agent information. Repair actual misstatements, not the safety gate. Move to a new unseen case after the first synthetic fixture passes.

## What is not measured

This evaluator uses **exact factual string matching** and checks action/approval ceilings. It cannot establish open-ended prose truth, visual quality, real page behavior, customer consent, correct pronunciation, live machine readiness, animation aesthetics or actual agent intelligence. It is not a security sandbox and does not authorize email, spending, deployment or human approval.

Next proof target: independent unseen cases from three capability families, model-generated responses, human-verified source judgments and measured pass/fail plus manual rework. Only then claim useful model performance. The dependency task `rovor-work-packet-contract` should reuse these formats, not introduce a second ownership queue.
